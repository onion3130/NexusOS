# NexusOS v1.9 — Assistant Memory & Confirmed Intelligence (plan)

**Status:** pending owner approval
**Version target:** v1.9.0
**Migration heads:** `0023_memory` (from `0022`)
**Last updated:** 2026-08-06

## Goal

Deliver the repeatedly deferred "autonomous semantic memory and model-written notes" — but safely, matching the NexusOS philosophy that AI output is untrusted: **every durable AI-derived write is a proposal the user confirms or rejects**, and every write is audited. v1.9 adds persistent assistant memory, model-proposed notes ("save this conversation as a note"), and a small read-only provider-health panel.

## Architecture

Three additive pieces on existing infrastructure:

- **Memory module** (`app/modules/memory/`): user-owned memories (durable facts/preferences), written only through confirmation. Grounded into assistant context as bounded, delimited, untrusted reference material on an explicit opt-in.
- **Model-proposed notes**: a new `notes.draft` assistant tool proposes title + content from the conversation; confirmation creates the note through the **existing** notes service, so drafts reuse versioning, chunks, FTS, and workspace behavior with no new tables.
- **Provider-health panel**: read-only aggregate AI status surfaced in the Assistant workspace.

Proposals reuse the existing assistant tool-call proposal pipeline (typed, expiring, CSRF-protected, idempotent, audited) — the same mechanism already used by task and maintenance actions. No new background jobs are required; memory is user-driven.

## Database changes (reversible migration)

### `0023_memory`

- `memories`: id, user_id, kind (`fact` | `preference`), content (≤ 2000 chars), source_conversation_id (nullable FK), status (`active` | `archived`), content_version, created_at, updated_at, archived_at, deleted_at.
- Indexes on `(user_id, status)`, `(user_id, created_at)`.
- No FTS in v1.9 (bounded top-N scan); FTS over memory content is flagged for a later increment.

## API endpoints

- `GET /api/v1/memory` (status filter, cursor), `POST /api/v1/memory` (manual entry), `PATCH /api/v1/memory/{id}`, `POST /api/v1/memory/{id}/archive`, `POST /api/v1/memory/{id}/restore`, `DELETE /api/v1/memory/{id}` — CSRF, `memory.read` / `memory.write`, ownership, audit, idempotency.
- Assistant proposals: `memory.remember` and `notes.draft` flow through the existing assistant proposal routes (propose → confirm/reject → execute service adapter).
- `GET /api/v1/system/ai/health` — read-only provider state, last success/failure timestamps, latency bucket, embedding index counts (extended), all redacted.

## Frontend components

- **Memory workspace:** list, add manual memory, edit, archive/restore/delete, and a proposal queue with confirm/reject states for `memory.remember` drafts.
- **Assistant workspace:** "Save as note" affordance (triggers `notes.draft` proposal → confirmation modal); a memory toggle in grounding options (`include_memory`); AI health status panel.
- **API client** (`lib/memory.ts` new, `lib/assistant.ts`, `lib/system.ts` updates).

## AI architecture

- **Tools:** `memory.remember` (propose a bounded memory entry) and `notes.draft` (propose bounded title + content). Both are read-only until confirmed; confirmation executes fixed service adapters (`create_memory`, `create_note`).
- **System prompt:** instructions to propose a memory when the user states a durable fact or preference, and to offer drafts when the user asks to save conversation content.
- **Memory grounding:** new `GroundingOptions.include_memory` (permission `memory.read`), bounded to ≤ 8 memories (term match + recency), injected as escaped, delimited untrusted context. Memory never grants tools, permissions, or host actions, and cannot override policy.
- No autonomous extraction, no model-written persistence without confirmation.

## Security considerations

- Confirmed-writes-only: proposals expire, require matching CSRF for cookie auth, and are ownership-scoped and audited; rejection discards nothing more than the proposal.
- Memory and draft content stay in the untrusted-content boundary (same treatment as notes and sources).
- Bounded lengths (memory ≤ 2000 chars; note title ≤ 160, content ≤ 20 000 chars) and bounded grounding counts.
- New permissions `memory.read` / `memory.write` are personal-data scope (owner + member), granted through the idempotent role refresh introduced in v1.8.
- Provider-health endpoint returns only redacted aggregate state.

## Raspberry Pi 5 considerations

Pure Python, no new runtime dependencies, no new worker load (no scheduled jobs). Memory rows are small; grounding scans are bounded. Provider-health reads existing status data.
